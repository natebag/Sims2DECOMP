### Pattern Analysis

DOL bytes show these functions:
1. Use `lis r9, XXXX; lwz r3, YYYY(r9)` (absolute addressing)
2. ALSO use `lwz r0, ZZZZ(r13)` (@sda21 addressing)
3. Have multiple `bl` calls to external functions
4. Have conditional branches (`beq`, `bne`)

When compiled with SN ProDG v3.93:
- Register allocation differs (different GPRs chosen)
- Instruction scheduling differs (instruction order)
- Same logic, different binary representation

### Root Cause

The SN ProDG compiler's:
- Register allocator chooses different GPRs than original
- Instruction scheduler orders instructions differently
- This is a **heuristic difference**, not a flag issue

Flags tried (that don't fix it):
- `-fno-schedule-insns` (helps PMF, not these)
- `-O2` (already using)
- `-G 8` (SDA threshold, already correct)

### Why This Is Hard

Unlike PMF/SDA where we could force specific codegen patterns,
instruction scheduling is deeply baked into the compiler's optimization
pipeline. We cannot force specific register choices or instruction
ordering through standard flags.

## POTENTIAL MITIGATIONS

### Option 1: Inline Assembly (Heavy-handed)
Wrap the entire function body in `__asm__` blocks.
- Pro: Exact byte match
- Con: Not real decompilation
- Con: Platform-specific

### Option 2: Accept Near-Misses (Pragmatic)
For functions where only register allocation differs:
- Accept `mr r3, r4` vs `mr r4, r3` patterns
- Functionally equivalent, different encoding
- Would need objdiff tolerance

### Option 3: Per-Function Tuning (Tedious)
- Try different C++ constructs to influence regalloc
- Use `register` keyword (deprecated, but may work)
- Add dummy operations to force spill/fill patterns
- Very time-consuming per function

### Option 4: Compiler Research (Long-term)
- Find undocumented SN ProDG flags
- Try older/newer ProDG versions
- Contact SN/INTERRUPT support (if possible)
